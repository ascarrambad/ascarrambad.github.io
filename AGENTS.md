# AGENTS.md

Guidance for agents working on this repository. This file applies to the entire
project.

## Project objective

Maintain a precise, compact engineering profile for Matteo Riva. The website is
an Astro-generated static site for GitHub Pages and should remain easy to keep
aligned with the CV.

Prefer clarity, factual accuracy, restrained typography, and maintainable data
over visual novelty or marketing language.

## Instruction priority

Apply guidance in this order:

1. The user's current explicit request.
2. This `AGENTS.md`.
3. The current Pages document and its PDF export for facts and visual reference.
4. The structured website data and implementation.
5. Historical material in `sources/v1/`.

If two authoritative sources disagree and the user's intent does not resolve the
conflict, report the discrepancy instead of silently choosing or combining
facts.

## Working method

For each task:

1. Read the relevant data, schema, component, styles, and source material before
   editing.
2. Keep the change focused; preserve established design and unrelated user
   work.
3. Keep data, validation, rendering, metadata, and asset endpoints synchronized.
4. Run checks proportionate to the change and inspect rendered output for visual
   or path-sensitive work.
5. Report what changed, what was verified, and any remaining uncertainty.

## Sources of truth

Use sources in this order:

1. The newest CV Pages document and matching PDF in `sources/` are authoritative
   for professional facts, dates, wording, and visual direction. They are
   currently named `matteoriva_cv_v14.pages` and `matteoriva_cv_v14.pdf`; a newer
   matching export supersedes them.
2. `src/data/profile.yml` is the website's structured mirror of that content.
3. `sources/v1/` is historical reference only. Do not restore its architecture
   or copy its content when it conflicts with the current CV.

Do not invent achievements, metrics, descriptions, technologies, or marketing
copy. Preserve apparently awkward CV wording unless the user asks to correct it
or the authoritative source is updated.

The CV filename may contain an internal version number. Do not display that
version number on the website.

## Technology and architecture

- Astro 7, strict TypeScript, static output.
- `src/data/profile.yml`: the only normal editing surface for profile content.
- `src/lib/profile.ts`: Zod schema, validation, inferred `Profile` type, and
  base-path-safe asset helper.
- `src/components/`: small presentational Astro components.
- `src/styles/global.css`: global responsive design system.
- `src/pages/index.astro`: composition only; do not move profile content here.
- Typed static endpoints publish the portrait and CV from `sources/`. Do not
  expose the full `sources/` directory as Astro's public directory.
- `.github/workflows/deploy.yml`: GitHub Pages deployment.
- `src/layouts/BaseLayout.astro`: document shell, canonical/Open Graph metadata,
  and Schema.org `Person` structured data.

When adding or changing structured content:

1. Update `src/data/profile.yml`.
2. Update the Zod schema in `src/lib/profile.ts` if the shape changed.
3. Consume the inferred TypeScript type in components.
4. Do not hard-code content in templates merely to avoid a schema change.

Use Markdown only if long-form project case studies are introduced. YAML is the
preferred format for CV-shaped records.

## Published asset contract

The website exposes stable public routes while keeping original documents under
`sources/`:

- `/matteo-riva-cv.pdf` is generated by
  `src/pages/matteo-riva-cv.pdf.ts`. Its source PDF path is hard-coded in that
  endpoint. When replacing or renaming the authoritative PDF, update the
  endpoint path and `cv.updated` in YAML. Keep `cv.url` on the stable public
  route unless the user explicitly requests a URL change.
- `/profile.jpg` is generated by `src/pages/profile.jpg.ts`. Its source portrait
  path is also hard-coded. When replacing the source portrait, update that
  endpoint; keep `identity.portrait` on the stable public route.

YAML contains public URLs, not repository filesystem paths. Do not copy all of
`sources/` into `public/` or expose editable/source document bundles.

## Employment data rules

Each employer requires:

- `company`
- `location`
- `period`
- `website`
- `description`
- one or more `roles`

The employer-level `period` must be one global range covering the earliest start
and latest end across every role shown for that employer. Only one range is
allowed, even when duties were non-contiguous. Role-level dates remain exact and
are displayed separately on the right.

Use CV-style date text consistently: `MM.YYYY — MM.YYYY`, `MM.YYYY — ongoing`,
or `YYYY — YYYY` where the source only gives years. Use an em dash with spaces
and lowercase `ongoing`. Do not infer missing months.

Current global ranges:

- Artificialy: `02.2026 — ongoing`
- Delvitech: `06.2023 — 01.2026`
- IDSIA: `03.2019 — 10.2022`
- Monkey Cube & ExMachina: `2014 — 2016`

Company website links and short descriptions belong in YAML, not in the
experience component. Verify external company URLs before changing them.

## Established visual direction

Do not perform a broad redesign unless explicitly requested.

- Compact CV-inspired layout with strong alignment and information density.
- Neutral gray profile header; white page; black typography and rules.
- Intentional black employer cards and labels with white text.
- All badge-like controls are squared. Do not reintroduce rounded pills.
- Dates on the right use squared black labels with white monospace text.
- Employer website controls are squared white labels inside black cards.
- Section headings are sticky below the top navigation and have no underline
  rule.
- The navigation has no MR/monogram block.
- The only CV download link is the black control at the top right.
- No permit field is shown. The birth date occupies that contact-grid position.
- Avoid gradients, shadows, color accents, glass effects, oversized marketing
  headings, slogans, and card-heavy landing-page patterns.

Typography uses the system Helvetica/sans stack for prose and a system monospace
stack for dates, navigation, labels, tags, and other machine-like metadata.
Maintain tabular numerals and the existing hierarchy. Refine rhythm and spacing
before introducing new font dependencies.

## Header animation

`src/components/TimeMachine.astro` is a self-contained inline SVG sketch beneath
the name.

- It is a black line drawing on a transparent background.
- It accelerates left to right, flashes, and disappears.
- Its 22-second cycle intentionally includes a long cooldown; do not make it
  repeat frequently.
- It must remain static when `prefers-reduced-motion: reduce` is active.
- Keep it dependency-free and decorative (`aria-hidden`).
- Do not replace it with the old raster DeLorean unless explicitly requested.

## Responsive and accessibility requirements

- Preserve semantic headings, lists, `dl` contact data, and accessible labels.
- Keep keyboard focus visible.
- External employer links need descriptive accessible names and safe `rel`
  attributes when opening a new tab.
- Mobile layouts must not hide content or introduce document-level horizontal
  overflow.
- Keep the sticky navigation and sticky section headings from overlapping.
- Preserve the reduced-motion fallback.
- Portrait cropping must keep the full hairline visible and the face centered.

## Metadata and public information

`BaseLayout.astro` emits canonical URLs, Open Graph tags, and Schema.org `Person`
JSON-LD. If identity, contact fields, portrait routes, or the page description
change, verify that visible content and metadata remain consistent.

Treat existing profile and CV information as intentionally public. Do not add
new personal identifiers, private contact details, analytics, trackers, or
third-party embeds without an explicit request.

## GitHub Pages and asset paths

The site supports both:

- `https://username.github.io/`
- `https://username.github.io/repository-name/`

Do not introduce root-relative generated asset URLs without using the existing
`publicAsset()` helper. Test both deployment shapes after path-related changes:

```sh
npm run build
GITHUB_REPOSITORY=ascarrambad/mriva-profile npm run build
npm run build
```

The final root build restores convenient local preview behavior.

Deployment runs from `.github/workflows/deploy.yml` on pushes to `main` and by
manual dispatch. Preserve static output and the repository-aware base path used
by `astro.config.ts`.

## Required checks

Node.js 22.12 or newer is required.

Before handing off code or content changes, run:

```sh
npm run format
npm run build
```

The build includes `astro check` and must finish with zero errors, warnings, and
hints. Also use `npm run format:check` when only verifying a clean tree.

For documentation-only changes, `npm run format:check` is sufficient. For
content, schema, endpoint, component, style, configuration, or dependency
changes, run the full build. Path-sensitive changes require both GitHub Pages
build shapes shown above.

For visual changes, inspect at least:

- desktop around 1440 px wide;
- mobile around 390 px wide;
- document `scrollWidth` equals viewport width;
- sticky heading position below the navigation;
- animation and reduced-motion states when relevant.

Before completing relevant changes, also confirm:

- exactly one visible CV download control remains, in the top-right navigation;
- no internal CV version appears in visible copy or metadata;
- no profile content was duplicated into an Astro template;
- source filenames resolve on the case-sensitive GitHub Actions filesystem.

## Editing discipline

- Preserve user changes and unrelated files.
- Prefer focused patches over rewrites.
- Remove obsolete fields, styles, endpoints, and imports when replacing a
  feature; do not merely hide them.
- Avoid adding frameworks, client-side state, runtime data fetching, or large
  dependencies for static presentation needs.
- Keep components focused and data-driven.
- Update `README.md` when development, publishing, or content-maintenance steps
  materially change.
